Proyecto 1 — Asistente RAG sobre los documentos de mi tesis doctoral

Autor: Pepe (José Jesús La Casa Nieto) Fecha: septiembre de 2026 Estado: planificación — sin código aún

1. Resumen ejecutivo

Este documento define el Proyecto 1 de un plan más amplio de mejora de perfil técnico: un asistente que responde preguntas en lenguaje natural sobre los documentos de mi tesis doctoral (papers, notas, borradores) usando RAG (Retrieval-Augmented Generation), construido como un agente (no una cadena fija) capaz de decidir entre consultar mis propios documentos o buscar papers nuevos en arXiv, con una pieza de automatización que mantiene la base de conocimiento actualizada sin intervención manual.

El proyecto persigue dos objetivos a la vez: ser una herramienta que uso de verdad durante el doctorado, y ser una pieza de portfolio que demuestra, con código real, la mayoría de los requisitos técnicos que piden las ofertas de "Ingeniero/a de Software — IA Generativa" que estoy usando como referencia de mercado (ver sección 8).

Contexto rápido para quien lea esto sin más contexto Soy ingeniero con formación en automatización industrial e IA, actualmente cursando un doctorado sobre sensores ópticos para monitorización online de bioprocesos con microalgas en fotobiorreactores abiertos. Hasta ahora he trabajado como Product Manager y desarrollador en un producto de ciberseguridad (detección de incidentes de red), con experiencia previa como ingeniero de IA/ML en otras empresas. Estoy reforzando mi perfil técnico (backend, APIs, MLOps) para volver a un rol más centrado en ingeniería.

2. El problema

2.1 Contexto personal

Durante el doctorado voy acumulando una cantidad creciente de documentos: papers propios, papers de referencia que leo, notas, borradores de capítulos. No tengo hoy una forma rápida de "preguntarle" a ese conjunto de documentos algo concreto — tengo que recordar en qué archivo estaba cada cosa, o releer por encima varios PDFs para encontrar un dato o una cita concreta. Además, mantenerme al día de papers nuevos publicados sobre mi tema (sensores ópticos aplicados a microalgas, monitorización online de bioprocesos) es un proceso manual que hago de forma irregular.

2.2 Problema concreto a resolver

  • Poder hacer preguntas en lenguaje natural sobre mis propios documentos de tesis y obtener una respuesta con las fuentes exactas de donde sale esa información (no quiero un modelo que "se lo invente" — necesito trazabilidad).
  • Poder preguntar por literatura reciente sobre mi tema sin tener que ir manualmente a buscar en arXiv cada vez.
  • Que el sistema se mantenga actualizado solo, incorporando papers nuevos relevantes sin que yo tenga que acordarme de hacerlo.

2.3 Por qué este proyecto (más allá de la utilidad directa)

Es el primero de los proyectos de mi plan de mejora de perfil porque cubre, casi al completo, la parte más nueva para mí y más demandada en el mercado ahora mismo: integración de LLMs en producción, RAG, agentes con LangChain/LangGraph, APIs con FastAPI, y buenas prácticas de ingeniería (testing, Docker, CI/CD). El detalle exacto de qué requisitos de qué ofertas cubre está en la sección 8.

3. Planteamiento de la solución

3.1 Enfoque general

El sistema tiene dos pipelines que comparten un mismo almacén de datos:

  • Pipeline de ingesta — mete documentos en la base de conocimiento. Se dispara de dos formas: manualmente (subo un PDF de tesis) o automáticamente (una vez a la semana, se buscan papers nuevos en arXiv relacionados con mi tema y se ingestan solos).
  • Pipeline de consulta — un agente construido con LangGraph recibe la pregunta, decide si necesita buscar en mis documentos, buscar en arXiv, o ambas cosas, y compone la respuesta final citando las fuentes.

3.2 Decisiones de diseño

Decisión — Orquestación: LangGraph en vez de un AgentExecutor clásico Ya tengo experiencia previa con LangGraph (lo usé en un pipeline de detección de incidentes). Un grafo explícito (nodo agente → nodos herramienta → nodo respuesta) es más fácil de depurar y de extender más adelante que la caja negra de un AgentExecutor tradicional, y es exactamente lo que piden las ofertas que uso como referencia.
Decisión — Base vectorial: pgvector sobre Postgres, no Chroma/FAISS aparte Necesito Postgres de todas formas para guardar usuarios, historial de preguntas y metadatos de documentos. Añadir pgvector evita sumar una pieza de infraestructura nueva (una base vectorial dedicada) solo para este proyecto — con el volumen de documentos de una tesis, el rendimiento de pgvector es más que suficiente. Si más adelante el proyecto creciera mucho, Chroma/Qdrant quedan como opción de migración, no como decisión de partida.
Decisión — API: FastAPI, autenticación JWT simple Un único usuario real (yo) al principio, pero implemento JWT desde el inicio porque es parte de lo que quiero demostrar que sé hacer, no porque lo necesite operativamente todavía.
Decisión — Extracción de PDFs Los documentos de tesis son PDFs con texto (no escaneados), así que basta con una librería de extracción de texto estándar de Python; no hace falta OCR.

3.3 Diagrama de arquitectura

Ambos pipelines comparten la misma base Postgres + pgvector: lo que entra por ingesta (manual o automática) es lo que el agente puede consultar.

4. Modelo de datos (esquema simplificado)

Cinco tablas en Postgres. Los nombres son orientativos, se pueden ajustar al implementar.

documentos
  id            uuid PK
  titulo        text
  fuente        text        -- 'manual' | 'arxiv'
  url_original  text null   -- si viene de arxiv
  fecha_ingesta timestamptz

chunks
  id            uuid PK
  documento_id  uuid FK -> documentos.id
  contenido     text
  embedding     vector(1536)   -- columna pgvector
  posicion      int            -- orden dentro del documento

usuarios
  id            uuid PK
  email         text unique
  password_hash text

historial_preguntas
  id            uuid PK
  usuario_id    uuid FK -> usuarios.id
  pregunta      text
  respuesta     text
  tool_usada    text        -- 'rag' | 'arxiv' | 'ambas'
  fecha         timestamptz

papers_arxiv_vistos
  id            uuid PK
  arxiv_id      text unique   -- para no re-ingestar el mismo paper dos veces
  fecha_vista   timestamptz
Nota papers_arxiv_vistos es la tabla que evita que la automatización semanal reingeste el mismo paper una y otra vez — antes de ingestar, se comprueba si el arxiv_id ya está.

6. El agente y sus herramientas

El agente sustituye a lo que en una versión más simple sería una cadena fija (LCEL). Recibe la pregunta y decide qué tool(s) usar antes de responder — no siempre las mismas, no siempre en el mismo orden.

Tool 1 — buscar_en_mis_documentos

  • Entrada: la pregunta del usuario (o una reformulación que haga el propio agente)
  • Acción: embeddings de la pregunta → búsqueda por similitud en chunks (pgvector) → top-k fragmentos
  • Salida: fragmentos + metadatos del documento de origen (para poder citar la fuente)

Tool 2 — buscar_papers_arxiv

  • Entrada: términos de búsqueda (el agente los extrae de la pregunta)
  • Acción: llamada a la API pública de arXiv, filtrando por categoría/tema relevante
  • Salida: lista de papers (título, autores, resumen, fecha, enlace)
  • Esta misma tool, reutilizada por el proceso de automatización semanal (ver más abajo), es la que decide qué ingestar

Automatización — ingesta semanal desde arXiv

  • Disparador: un job programado (cron simple o GitHub Actions con schedule), una vez por semana
  • Pasos: buscar_papers_arxiv con mis términos de interés → descartar los que ya están en papers_arxiv_vistos → para cada paper nuevo: descargar el PDF, chunking, embeddings, guardar en chunks
  • No pasa por el agente — es un script/pipeline directo, más simple y más barato de ejecutar que invocar un LLM para decidir algo que ya sabemos que hay que hacer cada semana
Decisión — por qué la automatización no usa el agente Un agente tiene sentido cuando hace falta decidir dinámicamente qué hacer. La ingesta semanal siempre hace lo mismo (buscar, filtrar duplicados, ingestar) — meter un LLM en ese bucle solo añadiría coste y latencia sin ningún beneficio. El agente es para cuando yo pregunto algo impredecible; la automatización es un pipeline determinista de datos.

11. Glosario rápido

RAG (Retrieval-Augmented Generation)
Técnica que combina búsqueda de información propia con un LLM generativo, para que la respuesta se base en documentos reales en vez de solo en lo que el modelo aprendió en su entrenamiento.
Chunking
Dividir un documento largo en fragmentos más pequeños antes de vectorizarlo, para que la búsqueda por similitud sea precisa.
Embedding
Representación numérica (vector) de un texto que captura su significado, usada para comparar textos por similitud.
pgvector
Extensión de PostgreSQL que añade un tipo de columna vectorial y búsqueda por similitud, convirtiendo Postgres en una base de datos vectorial.
Agente
A diferencia de una cadena (chain) fija, un agente decide dinámicamente qué acción tomar (qué tool usar, en qué orden) según la pregunta recibida.
Tool
Una función concreta que un agente puede decidir invocar (ej. buscar en una base de datos, llamar a una API externa).
LangGraph
Librería para construir flujos de agentes como un grafo explícito de nodos y transiciones, en vez de una caja negra.
LCEL (LangChain Expression Language)
Sintaxis de LangChain para encadenar pasos con el operador |, usada en cadenas fijas (no agentes).
JWT (JSON Web Token)
Estándar para autenticar peticiones a una API mediante un token firmado, sin necesidad de mantener sesión en el servidor.
